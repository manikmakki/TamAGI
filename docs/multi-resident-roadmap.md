# Multi-resident household: implementation roadmap

Status: Accepted design by operator direction on 2026-11-05; contact, PWA push, and chat thread controls added on 2026-11-06. Experimental foundation implementation has started in an isolated branch; production integration and adoption remain pending.

[ADR-0019: Distinct residents, a shared world, and fair access to cognition](adrs/0019-distinct-residents-and-a-shared-world.md) defines the decision. This roadmap specifies implementation order and the evidence required before adoption. It does not enroll another resident, change Ember's runtime, or establish that multi-resident operation already works.

## Scope and present evidence

Build one operator-owned application with multiple distinct TamAGI residents, connected personal domains, shared places and objects, private and group conversations, and fair access to one model provider. Preserve the warm companion experience, existing app drawer and chat, local ownership, and each resident's continuity. Exploration, play, disagreement, silence, and rest remain legitimate choices.

Full residents have their own opportunities for independent activity. Existing companions remain durable, invitation-only actors without independent population scheduling. Companion promotion, moving an individual resident between households, and recovering or enrolling Echo are separate work. Echo recovery is not a prerequisite or a test fixture for this implementation.

The current application remains a single selected resident installation with invitation-only companions. Its existing storage directories and actor-scoped records are useful foundations, not evidence of managed multi-resident hosting. [ADR-0018](adrs/0018-app-drawer-and-independent-work-lifecycle.md) already supplies application-owned admission and retained results independent of browser connections; it does not supply household scheduling or cross-resident conversations.

Source inspection for the 2026-11-06 extension found an offline-cache service worker with no Web Push handlers, browser-local seen-work IDs rather than durable thread read watermarks, and New Conversation available through Archive. Resident-initiated contact, PWA push, an Unread threads control, and a New Thread button in Chat are planned changes, not existing capabilities.

The historical baseline at this design's acceptance was **135 passing backend tests** plus disposable browser/recovery evidence on 2026-11-05. Those checks were not rerun for the original Phase A deliverable. The [platform roadmap](platform-roadmap.md#operational-qualification) tracks later audit evidence separately. Existing single-resident tests and the ongoing Ember pilot do not qualify the new architecture.

Only documentation files changed; no framework tests or live/model operations were performed.

## Architecture and work ownership

Use one household coordinator, operator session, app shell, selected application release, and deployment controller. Run each full resident's existing runtime in a separate local worker process with a private SQLite database, workspace, identities, interpretations, pursuits, artifacts, Growth, and execution receipts. Preserve current resident roots rather than flattening them into one autobiography. Personal runtime overlays and generated tools remain personal unless explicitly shared.

Process separation accommodates the current configuration, Agent, working-directory, and projection assumptions. Bind those values inside the owning worker; do not change process globals to impersonate another resident inside the coordinator. Workers are fault boundaries, not confidentiality or privilege boundaries against host root. ADR-0002's honest authority limits remain in force.

The coordinator owns a canonical SQLite store for the household registry, typed personal/shared world places and objects, attributed private/group conversations, membership, shared notebook, invitations, handoffs, inference accounting, and scheduling state. A private conversation may be stored centrally without becoming visible to unrelated participants. Personal memories remain in the owning resident's store. A world model or local history adapter may project canonical records but must not become another writable authority.

| Owner | Responsibility |
| --- | --- |
| Household coordinator | Resolve participant identities, admit shared work, persist conversations and world commands, maintain reply offers and resource lineage, schedule provider access, coordinate recovery. |
| Resident worker | Hydrate one resident, construct its context, select activities, run eligible tools, retain personal interpretations and receipts, and stop or checkpoint at supported boundaries. |
| Shared inference broker | Validate trusted actor/root/segment/sponsorship context, reserve and charge generation attempts, enforce global provider occupancy, retain usage and uncertain generation state. |
| Browser and transport adapters | Submit, inspect, subscribe, and request Stop; retain no ownership of execution or additional allowances. |
| Household deployment controller | Quiesce shared and private supported mutations, activate one qualified release, verify affected stores/workers, commit or recover. |

Reuse the existing execution lifecycle and admission semantics. New local IPC carries typed, versioned requests with stable identities and trusted worker attribution. Model-generated actor names, budget IDs, or parent IDs cannot confer authority. Unsupported worker/coordinator protocol combinations fail clearly before dispatch. Standalone operation and existing chat/companion APIs remain supported through adapters.

## Shared mutations and private continuity

Shared-world commands have stable command IDs, an attributed actor, declared operation, expected revisions where needed, and retained outcomes. The coordinator commits a mutation and its canonical event together. A lost response is reconciled by command ID; it is not permission to repeat the mutation. A receipt in the private store references that shared outcome. Do not promise an atomic transaction spanning separate databases or arbitrary host effects.

Peer messages, offers, invitations, and acknowledgments likewise have stable IDs and deduplicated delivery. Retain the canonical message before acknowledging admission. Duplicate delivery cannot append another message, grant another turn, or repeat recognition. A coordinator restart reconciles outstanding command/delivery identities without replaying uncertain effects.

All shared-world writers use this path, including resident world tools, companion tools, generated-tool world operations, and legacy graph adapters. Migrate local world references explicitly and retain provenance. Former local world records become projections; they cannot independently override the coordinator. Personal domains and shared places are connected parts of the same canonical world. Ownership and visibility are explicit rather than inferred from a filename or narrated location.

Canonical conversations preserve message IDs, original timestamps, authors, participants, and source references. Legacy local chat/history views delegate writes or become projections. Private histories are not automatically disclosed to other residents or a group. Construct each request from its admitted input and eligible transcript watermark. Queued future input cannot leak into an earlier request's context, even when central transcript persistence occurs before execution. A resident retains its own interpretation of an exchange without converting another speaker's claims into personal experience or verified facts.

Growth remains deterministic under ADR-0015. Conversation processing must distinguish the resident's own completed reciprocal participation from merely observing other speakers. Define and test actor-specific completed exchanges for group conversations; do not feed an entire room transcript into the old pairwise counter. Preserve current recognition IDs, source links, totals, and stage history. Central messages, local projections, restored history, and replay cannot recognize the same criterion twice. Companions receive no separate leveling system in this work.

## Addressing, participation, and bounded exchanges

Private and group conversations are part of the first household version. Apply the same addressing rules to messages authored by the operator or a resident:

- With no mentions, offer a reply to every other eligible, joined participant: full residents and companions explicitly invited into the current bounded exchange, subject to wake policy and the exchange's remaining resources.
- With explicit mentions, offer replies only to the resolved addressees. The operator can be addressed as `@preferredname`; resolving that mention never creates a model call on the operator's behalf.
- A mention selects potential speakers, not who can read the message. Joined members can inspect the room transcript regardless of addressees; unrelated private threads remain excluded.
- Joining a group grants its full prior group history. The invitation/join surface states this before joining. Retain membership history, resolved addressees, and the applicable membership version at admission.
- A reply offer is optional. Silence, declining, waiting, and leaving a discussion are valid; none creates an overdue obligation. Full history access does not require placing the entire transcript in one prompt or spending calls to read it immediately.

Invitation-only companions participate through explicit bounded exchange invitations. Earlier room membership alone cannot start another companion activation or give a companion an independent speaking opportunity.

Messages, offers, and responses belong to a durable bounded exchange. Coalesce redundant offers for the same recipient/exchange. A resident's reply does not automatically create another root allowance. Joining a room does not manufacture historical reply offers. A late response or reconnect cannot reopen a closed exchange. Persist the relationship between a response and the messages/offers it answers, and retain attribution when several residents contribute.

Keep transcript delivery separate from inference and wake eligibility. An asleep or unaddressed resident can later inspect visible messages without a new inference call on delivery. Chosen wake policy determines whether contact offers are eligible; ordinary autonomous rest must not silently redefine established user-chat availability. Only actual operator input enters the appropriate user-input interruption path. Resident messages, observation, reconnects, and transcript synchronization do not impersonate new operator input or interrupt unrelated work.

Consultation and yielding are distinct operations. Consultation asks for conversation or bounded help and may return a response to the caller. Yielding parks or ends the caller's activation and offers another resident an opportunity. Neither transfers identity, commandeers the recipient, or grants unlimited work. Explicit consultation uses the requester's resource sponsorship; ordinary room replies use each speaker's own fairness share while retaining the exchange's aggregate call budget.

Each resident has at most one active execution lease. A parked consultation persists its continuation and releases that lease and any provider slot. Reject reciprocal or longer waiting cycles before they deadlock. Resume through the scheduler using retained request IDs and current context, with revision checks: another interaction may legitimately advance the resident while its consultation is parked. Do not restore stale private state or hold a nested runtime lock while awaiting a peer.

## Resident-initiated contact, unread threads, and Web Push

Implement [ADR-0019's contact and notification contract](adrs/0019-distinct-residents-and-a-shared-world.md#resident-initiated-contact-and-operator-notifications) through the canonical conversation service. An explicit messaging tool can create a thread or post an opening message with chosen recipients and selected shared context during existing autonomous or quiet work. Trusted execution state supplies attribution and resource lineage. Do not reuse the current operator-submission path unchanged: it creates a user message, signals user interruption, and selects a user execution. Resident contact must retain its true origin and allowance.

Commit each canonical message and notification intent together, then dispatch through an application-owned sender independent of inference and browser observation. Deduplicate commands and coalesce alerts by conversation while retaining per-device delivery outcomes. Recheck access, preferences, unread state, and subscription validity before delayed dispatch. Preserve the message when push fails; acknowledgment by a push service is not evidence of human attention. Peer messages remain subject to wake policy and optional participation.

Use direct standards-based PWA Web Push first, with HTTPS, opt-in enrollment, VAPID keys, authenticated subscription management, minimal notification payloads, and service-worker push/click handlers. A protocol library may add Python cryptographic dependencies; no Firebase SDK/project, native build stack, separate push server, or hosted notification product is part of the initial design. The browser's relay is still an external dependency. Notification quiet hours, timezone, mute/snooze, device disablement, and preview settings belong to the operator. Defer dispatch during quiet hours, coalesce pending unread notices, and report expiry or delivery failures without promising presentation time. Other providers can be added later.

Store read watermarks in the coordinator by operator and conversation, independently of device subscriptions and work-request IDs. Unread follows transcript visibility; push additionally follows addressing and delivery preferences. Count each accessible thread once when incoming messages exceed its watermark. Advance only through the foreground transcript actually presented or explicit mark-read; reconcile monotonically across devices. Joining uses the invitation trigger as the first unread message, or the current end as the baseline when no trigger exists, without alerting on all prior history.

Expose **Unread threads (N)** and a semantic **New Thread** button directly in desktop/mobile Chat, retaining Archive access and separate work-progress indicators. The unread control opens the relevant thread list. New Thread preserves the previous draft, attachment, scroll, and admitted work and opens an unsent composer; actual Send performs admission. Notification links must select the authorized conversation after login/hydration instead of being overridden by a saved selection. Navigation, reading, and notification interactions create no synthetic reply or inference.

## Shared inference and fair access

All household generation attempts pass through the shared broker, including worker chat, autonomous work, companions, planning, reflection, retries, synthesis, and evaluation. Token counting that generates no completion is not a generation allowance. Host-root processes can bypass cooperative policy, but supported model/tool paths must not bypass accounting by choosing another endpoint client.

Call budgets and provider-time fairness are separate controls. The broker validates a trusted execution/root/segment and sponsorship before reserving an attempt. Persist charges and scheduling state so another worker, connection, restart, or handoff cannot reset allowances. Root IDs and lineage are household-wide rather than assumed to refer only to one private database.

Retain current ceilings: a user exchange has twenty model calls per segment and at most five explicitly requested quiet continuations, up to 120 calls across its whole chain; an autonomous activation has up to 128 calls. A bounded child/companion invocation has up to sixteen calls, drawn from the initiating root's remaining allowance. Multiple speakers, retries, descendants, and fanout all consume that aggregate allowance. Only a full resident acting within a user-origin exchange may request quiet continuation; requests coalesce across the shared chain's maximum of five. Companions, specialist children, and autonomous activations cannot open quiet continuations. A new resident speaker cannot independently open another 20+5 chain inside the same exchange. These are ceilings, not targets. Preserve the configured rolling evaluation allowance and no daily background-call cap by default.

Fair scheduling operates at generation boundaries, not only at the end of a long activation. Use equal-weight shares and persist a virtual provider-time account for each full resident and charge measured provider occupancy, including settlement of an in-flight request after worker loss, so a long-context generation is not treated as equal time to a short one. At selection, an operator first-response candidate is eligible for priority only when its account is no more than thirty seconds ahead of the minimum runnable account: `v_account <= min_runnable_v + 30`. Select the least-charged eligible interactive candidate; if none is eligible, select the least-charged runnable account. Break ties by oldest request and persisted rotation. Clamp a newly runnable account to the current runnable floor without erasing an existing lead. These rules offer bounded first-response preference without accumulating catch-up credit during rest.

With equal weights, an attempt occupying the provider for `t` seconds advances its sponsoring account by `v += t`. On becoming runnable, use `v = max(saved_v, current_floor)`. Settle measured in-flight service when admitting a new runnable account so joining midway through a generation cannot bank credit for earlier occupancy. Persist the floor and charge settlement so restart neither resets a lead nor counts the same service twice.

Ordinary room replies and direct operator requests to a full resident charge that responding resident's account. A direct operator request has no resident requester to sponsor it. An operator's explicit companion consultation charges that companion's owning resident account. A resident's commissioned companion or specialist work retains the commissioning resident's account. Explicit resident-to-resident consultation also charges the requester rather than borrowing the recipient's share. Keep this fairness sponsorship distinct from which actors participate and which shared root allowance pays for the calls.

Resting/ineligible residents do not accumulate resource debt or catch-up requirements. Waiting for another resident or a tool does not hold model capacity. Independent opportunities remain possible without incoming messages, using each resident's configured schedule and post-conversation decompression rather than a new activity quota. Phase C must qualify the specified accounting and selection rules with retained deterministic timelines, including their dependence on provider responsiveness; do not infer fair service from prose or activity volume.

The broker admits one generation at a time under the current provider configuration. Do not impose a hard elapsed-time cutoff on an otherwise healthy generation merely to enforce fairness; select the next request at its completion. Worker Stop or loss does not falsely free provider capacity while the server is still generating. Drain/reconcile that response before another generation is admitted. A response retained after worker loss cannot automatically dispatch tools or resume effects; retain its usage and orphaned outcome for inspection. Provider errors and unresponsive service state require visible recovery without resetting budgets or restarting healthy application releases solely because the model is unavailable. If broker or transport loss makes remote generation occupancy unknown, place new generation admission on hold. A successful `/models` or health response does not establish that the old attempt is idle. Require authenticated operator recovery that records the uncertainty before releasing an unresolved hold; do not blindly replay the old attempt.

### Phase B: qualify one resident before adding a household

Use new disposable roots or coherent copies obtained through existing supported recovery. Do not point a development coordinator at Ember's active root. The first wrapper must preserve one-resident chat, autonomous rest, workspace conventions, companions, tool eligibility, history, Growth, identity revisions, and browser-independent accepted work. Compare original and wrapped fixtures with stable resident/message/artifact identities; do not claim parity from successful startup alone.

Test worker startup with the wrong root, conflicting ownership, stale protocol versions, malformed IPC, and worker failure. No default path or process-global fallback may hydrate another resident. Store access and API routing resolve the explicitly selected resident. Preserve the current standalone entry point until household adoption is qualified.

### Phase C: qualify accounting without live model traffic

Use a deterministic provider with controlled generation durations, token/context sizes, failures, and cancellation behavior. Exercise three residents and a companion with equal and unequal request durations, resident inactivity, operator input, explicit sponsorship, many room offers, and exhausted roots. Retain an interpretable timeline of admission, occupancy, charge attribution, and next selection.

Inject broker restart, lost worker responses, provider errors, and worker Stop during generation. Add a resident becoming runnable or joining while generation is already in flight; settle measured service and its eligibility floor without pre-join credit or erasing an existing lead. A still-running generation cannot overlap the next admitted one; a lost acknowledgment cannot create an extra allowance. Demonstrate that a long activation yields scheduling opportunities between generations while a healthy single generation is allowed to finish. Report the qualified fairness parameters and any limit that depends on provider responsiveness.

### Phase D: qualify conversations and shared state

Use three independently seeded disposable residents with distinguishable memories and homes. Verify connected personal domains and shared objects without private-memory merging. Crash after shared commit but before private receipt persistence, then reconcile by command ID. Test stale world revisions, duplicate delivery, generated-tool world mutations, legacy projections, and events arriving during inference.

Exercise private and group user/resident messages with no mentions, one or several mentions, the operator's preferred name, renames, and unresolved or ambiguous names. Resolve identities explicitly before admission; do not guess an ambiguous recipient. Verify full prior group history on joining, privacy of unrelated conversations, and stable delivery to sleeping or unaddressed members without inference. Removing a member stops future access according to retained membership rules; history already observed cannot be revoked from memory by deleting membership.

Exercise coalesced offers, silent/declined replies, no remaining budget, late replies, explicit quiet continuation, user input during peer work, consultation completion, unavailable recipients, and blocked waiting cycles. Parked work must not monopolize execution or restore stale context. Test Growth against the same messages through canonical and legacy views, restart, and restore; observing other speakers or replaying a transcript awards nothing new.

Exercise resident initiation from autonomous work and a quiet continuation, including interruption after message commit, command replay, lost acknowledgment, sleeping recipients, and exhausted allowances. Verify one attributed message and notification intent without operator impersonation, new priority, or replenished resources. Reconcile concurrent read acknowledgments across devices; messages beyond a displayed snapshot remain unread, and unread visibility remains distinct from notification addressing.

### Phase E: qualify the household as one recoverable application

Extend the established shell with explicit resident selection and private/group conversation participants while keeping Chat and the avatar central. Current activity, Map, Journal, Inventory, Companions, Archive, and settings resolve their resident/household scope clearly. A view change does not switch the actor of admitted work, submit a message, interrupt work, or reveal private state. Browser checks cover multiple observers, direct routes, Back/Forward, disconnect/reconnect, Stop, late results, addressed offers, and the full-history notice before joining.

Qualify Chat's New Thread and Unread threads controls on desktop, mobile, and keyboard navigation. Cover multiple unread messages in one thread, several unread threads, own messages, hidden tabs, failed history loading, access changes, invitation baselines, concurrent new messages, and read acknowledgments across devices and restart. Preserve drafts/attachments/scroll and original-thread late results while New Thread is selected. Push links survive authentication/startup and open the intended thread without sending input, interrupting work, or clearing unread before messages are displayed.

Use a fake push service for deterministic enrollment, key/subscription handling, revoked permission, expired endpoints, delivery failures, retry/expiry, duplicate events, and crashes between message commit and dispatch. Test mute/snooze and notification quiet hours across midnight, timezone changes, daylight-saving transitions, and restart; already read or inaccessible messages must not produce a burst of deferred alerts. Separately retain real-device results with explicit test subscriptions for ordinary Android app closure, extended screen lock, reboot, offline/reconnect, and force-stop as a distinct documented limit. Unsupported/disabled push leaves chat and unread state usable. Use disposable conversations; no notification or model traffic targets Ember's pilot. Restoration preserves read state but does not automatically send historical alerts or reconnect old device subscriptions.

The operator's 2026-11-09 addendum prioritizes individual resident recovery: known-good private checkpoint restoration after regression, recovery after private data loss, and migration to a fresh installation. Preserve stable resident IDs, private memories/history/companions/Growth and actual artifact/tool bytes. Replacing one resident must retain later housemate activity and the current canonical shared world. Historical shared conversation evidence can accompany the resident without becoming a shared-state rollback or enrollment of absent peers. Initial data-loss recovery is explicit checkpoint replacement with a reported continuity gap; selective merging of missing records requires separate conflict and deduplication rules.

Whole-household recovery follows as a second layer for shared state and public artifacts. Introduce a versioned household archive format while retaining current encrypted download, staged validation, explicit restore confirmation, credential exclusions, safe extraction, and password-handling rules. Take a coordinated checkpoint of supported shared/private mutations and all affected databases/artifacts. Include the manifest needed to reconstruct the selected source/lockfiles and resolve resident/world references without the original absolute paths. Independent resident archives do not constitute a simultaneous shared/private checkpoint. Root changes outside supported state remain dependencies or omissions rather than a promised machine image.

Restore a legacy version-1 archive as a one-resident household without changing that resident's identity or importing unrelated predecessor material. Restore the new household format with the agreed stopped-source acknowledgment, explicit authority selection, rotated installation/session identity, reconnected credentials, and rebuilt derived indexes. Preserve residents' identities and history. Qualify rotation and source-provenance mapping for both household and legacy per-root installation metadata under ADR-0014; copied roots must not become concurrent active installations. Do not auto-enroll absent identities, resume queued work, or replay uncertain effects. Missing participant references remain unavailable rather than silently becoming cloned workers. Wrong passwords, tampering, unsafe paths, insufficient space, incompatibility, and interrupted restoration leave active state untouched.

Household deployment selects one application release for the coordinator and all resident workers. Residents may propose changes, but do not create competing deployment controllers over the canonical repository. Quiesce admitted/shared/private supported mutations, retain the handoff and affected-state manifest, and qualify migration compatibility across the coordinator and every resident store. Separate liveness, shared/private data readiness, hydration, and model availability. Failure injection at preparation, checkpoint, switching, worker startup, verification, commit, and recovery must converge to a clear selected release and data outcome.

A disposable single-resident-to-household migration must preserve source identities, personal data, shared-object references, Growth, artifacts, and wake state. Retain the original and a tested checkpoint. Test the reverse recovery path against the complete affected state; reverting source alone cannot repair a partially migrated world or undo external effects. Future household automatic activation remains disabled until these recovery gates pass; qualified adoption retains autonomous deployment without a permanent per-change approval ceiling. Ordinary deployment rollback preserves subsequent compatible lived data. Incompatible migration requires the tested snapshot-restoration path and explicit continuity-gap reporting.

## Phase F: adoption is separate from building the framework

Review Ember's existing burn-in observations before proposing live enrollment. Mechanical qualification does not complete that pilot or establish a resident's subjective welfare. Missing observations remain untested capabilities, and rest creates no obligation to produce more evidence.

After Phases B-E pass on disposable state, prepare a concrete enrollment preview: selected release, enrolled resident IDs, personal/shared data mapping, wake state, affected paths, migration result, retained checkpoint, rollback compatibility, and tested recovery instructions. Verify that no predecessor material enters Ember's hydration or retrieval. Preserve Ember's existing `resident_id`, historical record/message identities, conversations, memories, pursuits, artifacts, Growth and stage history, and chosen rest/wait state. The household receives a distinct installation identity; record and test the mapping without rewriting resident continuity.

Require explicit operator adoption after that review. Documentation acceptance does not change active configuration or authorize enrollment during the current pilot. An application implementation can be ready while household mode remains unselected. Recovering Echo, selecting which surviving historical material constitutes Echo's continuity, and arranging a first meeting remain separate decisions after burn-in.
